## Update 3 (root cause found and fixed: training on non-causal transitions)

The real root cause was upstream of everything diagnosed in Updates 1-2:
`marl/rollout.py`'s `collect_rollout` was calling the actor and recording an
RL transition on **every low-level simulation step**, but `env.step()` only
ever applies the sampled action when that robot is actually at a high-level
decision point (`should_trigger_high_level`) — on all other steps the env
silently ignores the sampled action. So the vast majority of recorded
transitions had a reward that was causally disconnected from the action
attributed to it, which floods the policy gradient with noise no amount of
reward shaping, entropy tuning, or initialization fixing (Updates 1-2) could
fully overcome.

Fix (now implemented and verified):
1. `collect_rollout` now only queries the actor / records a transition at
   actual high-level trigger points, and accumulates reward across all the
   low-level steps a decision spans until the next trigger (or episode end)
   before finalizing that one transition — proper semi-MDP / options-style
   credit assignment instead of one transition per simulation tick.
2. `ResidualFrontierActor` / `action_logits` now accept a `special_mask`:
   when a robot has no active target and at least one valid frontier exists,
   the "continue"/"release" special actions are masked out entirely, so the
   policy is structurally prevented from idling instead of just being
   softly discouraged from it.
3. `ExecutionAwareVoronoi.assign_unique_frontiers` + `rollout.build_joint_decision_inputs`
   jointly bias (not force — residual `delta` can still override modestly,
   though the +2.0 shaping penalty is larger than `delta`'s `tau`-bounded
   range so it dominates in practice) robots deciding in the same step away
   from picking the same physical frontier.

Verified with the same 200-iteration sanity check used throughout this doc
(`results/sanity_check_v6/train_log.csv`), compared to v3-v5:

| run | mean coverage | % iters flat at 0.1406 | max value loss | first-50 vs last-50 mean coverage |
|---|---|---|---|---|
| v3 | 0.157 | 58% | 2931.7 | 0.193 -> 0.142 (degrades) |
| v4 (return norm + value clip) | 0.160 | 66% | 10.0 | 0.205 -> 0.141 (degrades) |
| v5 (+ collision-stall fix) | 0.163 | 68% | 8.2 | 0.208 -> 0.143 (degrades) |
| **v6 (+ this fix)** | **0.215** | **20%** | **3.9** | **0.219 -> 0.213 (holds)** |

v6 is the first run where late-training coverage does not regress back
toward the flat floor — exploration is sustained, not just present early and
then abandoned. Updates 1-2's fixes (init bias, return normalization, value
clipping, collision-stall recovery) were real and are still worth keeping,
but they were treating symptoms of this deeper issue, not the cause.

**Remaining minor gap, not yet fixed**: `pending` (the in-flight
decision/reward accumulator in `collect_rollout`) is a fresh local dict each
call. A decision still in flight when one `collect_rollout` call ends is not
carried over into the next call's `pending`, so the reward from the first
few low-level steps of the next rollout (before that robot's next trigger)
is silently dropped rather than attributed anywhere. Likely a small effect
given rollout_length >> max_high_level_interval, but worth fixing for
correctness if pursuing precise return accounting later.

## Update 3 (reward and high-level credit fixes implemented)

The collision-stall fix alone did **not** solve collapse. Loading
`results/sanity_check_v5/checkpoint.pt` still showed the trained actor choosing
`K+1`/`RELEASE_ACTION` with ~0.9 probability in the initial state. Further
debugging found and fixed three stronger causes:

- Reward was still anti-exploration even without collisions: an 80-step
  nearest-frontier episode reached coverage `0.3984` but returned `-20.19`,
  while always-release returned `-1.6`. Root causes were `path_cost` charging
  remaining path length every step and `comm_count` treating every target
  assignment as communication. Fixed by charging path cost as actual per-step
  displacement and making target-assignment communication cost opt-in via
  `reward.charge_target_assignment_comm=false`.
- PPO rollout was training on actions the env never executed. `collect_rollout`
  sampled actor actions every low-level step, but `env.step()` only applied
  them when `high_level_triggered=True`. Fixed by recording only executed
  high-level decisions and accumulating low-level rewards back to that pending
  high-level transition.
- Global coverage reward created a lazy-agent/free-rider signal: a robot that
  released could receive coverage reward generated by its teammate. Fixed by
  assigning each robot only its own incremental coverage contribution from its
  observation update.

Two more action-prior fixes were added after v7 still showed release collapse:

- Special actions are now state-masked: if a robot has no active target and
  there is at least one valid frontier, `CONTINUE_ACTION` and `RELEASE_ACTION`
  are masked out. They are allowed when a robot has an active target or when no
  frontier is valid.
- `collect_rollout()` now uses a joint decision builder that applies
  ExecutionAwareVoronoi assignment as a multi-robot prior. The builder biases
  each robot toward a unique assigned frontier by frontier id, rather than
  letting symmetric robots independently see the same cheapest token.

Fresh verification after these changes:

- 49/49 unit tests pass (`python -m unittest discover -v`).
- v8 (`results/sanity_check_v8_special_mask`) improved mean train-log coverage
  to `0.2138` and reduced initial-coverage rows from ~130/200 to 40/200.
- v9 (`results/sanity_check_v9_joint_voronoi`) has mean train-log coverage
  `0.2151`, max `0.3633`, and stable value loss (max `3.88`).
- Greedy evaluation of the v9 checkpoint on the 80-step office sanity env using
  the joint decision builder: final coverage `0.3711`, return `+0.4636`, zero
  collisions, zero overlap steps. Action index counts were `{0:29, 1:3, 9:32}`;
  env target counts included multiple unique frontier ids, not pure release.

Remaining caveat: `scripts/train.py` still logs the env's current coverage at
the end of each rollout; because `collect_rollout()` resets the env inside a
rollout when an episode ends, this column is useful but not a clean episode
performance metric. Next best step is to add an evaluation/checkpoint script
that reports final coverage, return, collisions, overlap, and action
distribution across multiple seeds/map types.

## Update (after this doc's original "recommended next step" was implemented)

Codex implemented the return-normalization + value-clipping fix this doc
recommended (`RunningMeanStd`, `compute_value_loss` with PPO2-style clipping,
`approx_kl` logging, `--no-normalize-returns` / `--value-clip-eps` CLI flags
in `scripts/train.py`). Reviewed the implementation — it's a correct, standard
implementation (Chan's parallel-variance merge for the running stats, the
usual `max(unclipped, clipped)` value-loss formula, k1/k3 approx-KL
estimator). 42/42 tests pass (Codex added `tests/test_mappo_stability.py`
and an actor init-bias test).

Re-ran the same sanity check (`results/sanity_check_v4.log` /
`results/sanity_check_v4/train_log.csv`, same command as v1-v3, see below):

- **Value loss is now genuinely stable**: max value loss across 200
  iterations is `~10.0`, vs `~2700+` repeatedly in v3. This confirms
  "un-normalized return targets destabilizing the critic" was real and is
  now fixed.
- **Coverage still collapses**, just less absolutely: instead of permanently
  flatlining at `0.1406` from one point onward (v1-v3), v4 alternates
  between exploring (`0.18-0.34`) and reverting to `0.1406`, with brief
  re-exploration attempts around iter 96/111/158-159/170-171 that don't
  stick. So critic instability was a real, now-fixed bug, but it was not the
  root cause of the exploration collapse — it was making an already-present
  problem noisier/worse.

This now isolates the remaining variable cleanly: with the critic stable,
`entropy_coef` / reward-weight rebalancing experiments (attempted in v3,
inconclusive because the critic was too noisy to trust at the time) are
worth retrying for real. Suspect the collision penalty (`w_collision=5.0`)
still structurally dominates typical per-step coverage gains even at
`w_coverage=10.0`, since advantage normalization (not return normalization)
governs the policy gradient and a single collision event is still a much
larger single-step reward swing than typical coverage deltas.

**Next concrete experiment**: with v4's normalization fix in place, sweep
`entropy_coef` higher (try `0.1`, `0.2`) and/or reduce how punishing a single
collision is *relative to a full episode* (e.g. only penalize collision
while also zeroing velocity, not stacking it every stuck step via
`stuck_counter`-scaled penalties — check whether `aggregate_reward` is being
called with `collision=True` for many consecutive steps after a single bump,
which would compound the penalty far beyond what one bad action should
cost). Re-run the same sanity-check command and check whether the
exploring/reverting oscillation in `coverage` resolves into a sustained
upward trend instead.

**Confirmed, not just speculation**: ran an 80-step episode with a fresh
(untrained) actor and counted `robot.in_collision` — it was `True` for 15 of
80 steps, including a streak of **9 consecutive steps**. Because
`compute_command` zeroes velocity while `in_collision`, the robot doesn't
move away on its own, so `in_collision` (and therefore the `-w_collision`
penalty) keeps firing every single step it stays stuck. A single bad
movement choice can cost `9 * -5.0 = -45` in one streak, versus a typical
per-step coverage reward of `0.01-0.5` even after the `w_coverage=10.0`
bump. This is the most concrete lead so far for why the policy keeps
re-learning that not moving is safer than moving. Worth fixing two ways,
either or both:
1. **Recovery behavior**: when stuck, the controller should actively try to
   back away / replan instead of just zeroing velocity and waiting — right
   now "stuck" is a stable equilibrium for the low-level controller, not
   just for the policy.
2. **Reward shaping**: penalize the collision *event* (e.g. only on the
   transition into collision, or cap how many consecutive steps it can be
   charged) rather than charging it every step of an indefinite stall.

## Design decisions already made — don't relitigate without discussion

- `CONTINUE_ACTION = -1`, `RELEASE_ACTION = -2` are defined in
  `multi_robot_exploration_env.py` (the env owns its action contract).
  `marl/action_adapter.py` imports them from there, not the other way around.
- Actor's action space is `K + 2`: indices `0..K-1` pick a top-K frontier
  token, index `K` = "continue current target", index `K+1` = "release/idle".
- `c_analytic` fed to the actor is the real `ExecutionAwareVoronoi` cost for
  that robot's top-K tokens (`marl/rollout.py:build_decision_inputs`) — this
  is the "residual actor refines the analytic Voronoi assignment" story, keep
  it wired this way.
- `OccupancyGrid.get_global_bev()` (used for the centralized critic) must
  only ever read `env.grid` (the team's currently-explored map), **never**
  `env.true_cells` (hidden ground truth). This is what keeps the "unknown
  environment" / CTDE framing valid for the paper — do not pass `true_cells`
  into anything the actor or critic sees.
- GAE must be computed **per agent** (`mappo._prepare_multi_agent_batch`)
  before concatenating into one batch for the PPO minibatch loop — agents'
  per-step transitions are not a single contiguous trajectory, so
  `compute_gae` would silently miscompute advantages if you fed it one
  flattened multi-agent buffer directly.

## Bugs found & fixed this session (context only, already done)

- Env reward function had 5 of its 6 weight terms (`w_path`, `w_collision`,
  `w_overlap`, `w_comm`, `w_frontier`) wired to dead/hardcoded values — fixed
  by actually connecting `LocalController`, collision detection, shared-target
  overlap, and frontier-arrival bonus into the reward.
- `frontier_id` assignment in `cluster_frontiers` depended on Python
  set-iteration order and could silently reassign to a different physical
  frontier between steps — fixed with a stable sort key.
- `comm_aware=False` branch of `overlap_risk` was reading a peer's real
  `target_frontier_id` anyway (information leak) — fixed.
- `nn.MultiheadAttention` could emit NaN when a robot has zero valid
  frontier tokens (fully-masked row) — fixed by temporarily unmasking
  all-masked rows (output gets zeroed afterward anyway).
- `robot.path` (used for `path_cost` in the reward) was never shrunk as the
  robot advanced along it, so "having an active plan" cost a constant
  penalty every step regardless of progress — fixed by popping reached
  waypoints.
- `ResidualFrontierActor.special_head`'s final-layer bias is now initialized
  to `-2.0` (`marl/actor.py`) so "continue"/"release" don't start with an
  unearned logit advantage over real (negative-cost) frontier picks.

## Unresolved problem: policy collapses to "always release" (do nothing)

Ran `scripts/train.py` with `--iterations 200 --rollout-length 32 --map-type
office --map-size 8 --resolution 0.5` three times, changing one thing each
time. Logs are in `results/sanity_check_*.log` / `results/sanity_check_*/train_log.csv`.

1. **v1 (no actor-init fix)**: `coverage` flatlines at `0.1406` from
   iteration ~0 — policy never explores at all, greedy action is always
   `RELEASE_ACTION` even on a freshly initialized (untrained) actor. Root
   cause confirmed via direct logit inspection: `frontier_logits =
   -(c_analytic - delta)` starts negative (cost >= 0), while
   `special_head`'s raw output starts near 0, so the "release" logit beats
   every real frontier option before any training happens.
2. **v2 (added the `-2.0` special-head bias init)**: `coverage` now varies
   `0.14–0.32` for ~125 iterations (policy genuinely explores at first),
   confirming the init-bias diagnosis was real — but the policy **re-collapses
   to flat 0.1406 around iteration ~130** and stays there.
3. **v3 (also bumped `entropy_coef` 0.01->0.05 and `w_coverage` 1.0->10.0,
   plus the `robot.path` shrink fix)**: collapse happens **earlier** (~iter
   42-60), and value-loss spikes into the 1000s are **more frequent**, not
   less. This rules out "just rebalance the reward weights" as a sufficient
   fix.

Why v3 likely made it worse: `mappo.update()` normalizes **advantages** per
batch (`full.adv = (full.adv - full.adv.mean()) / (full.adv.std() + 1e-8)`)
before the policy-gradient loss, which neutralizes most of the effect of
scaling `w_coverage` on the actor's gradient (only relative ordering within
the batch matters once normalized). But **returns** (the critic's regression
target, `value_loss = ((values - batch.returns) ** 2).mean()`) are **not**
normalized anywhere. Scaling `w_coverage` 10x increased the variance of
per-step rewards/returns (occasional large coverage jumps now contribute up
to 10x more), which plausibly destabilized the critic further (more frequent
huge value-loss spikes in v3 than v2), and a noisier critic produces noisier
advantages, which can push the policy back toward the low-variance "do
nothing" fixed point faster.

## Recommended next step (not yet implemented)

1. **Add return/reward normalization** — track a running mean/std of
   returns (or rewards) across training iterations (a `RunningMeanStd`-style
   accumulator is the standard approach, e.g. as used in CleanRL/SB3) and
   normalize the critic's regression target before computing `value_loss`.
   Per-batch advantage normalization alone is not enough because it doesn't
   touch the critic's training signal.
2. **Add value-loss clipping** (PPO2-style): clip the new value prediction
   to within `clip_eps` of the old value estimate before computing the
   squared-error loss, same spirit as the existing policy-ratio clipping in
   `mappo.update`. Requires storing `old_value` per transition (already have
   `values` in `RolloutBatch`, just need to use it as the clip anchor).
3. Re-run the same sanity check:
   ```
   python scripts/train.py --iterations 200 --rollout-length 32 --n-robots 2 \
     --map-size 8 --resolution 0.5 --sensor-range 1.5 --sensor-rays 36 \
     --map-type office --max-episode-steps 80 --frontier-k 8 --d-model 64 \
     --update-epochs 4 --minibatch-size 64 --output-dir results/sanity_check_v4 --seed 0
   ```
   Check `results/sanity_check_v4/train_log.csv`: value loss should stop
   spiking into the hundreds/thousands repeatedly, and `coverage` should show
   sustained variation or an upward trend instead of flatlining at `0.1406`.
4. Only after (1)-(2) are in and verified should `w_coverage` /
   `entropy_coef` / `w_collision` be revisited — tuning weights before the
   critic's training target is normalized is likely to keep producing
   confusing, noisy results.
